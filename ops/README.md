# תפעול — שני מופעים על שרת אחד

## כתובות קבועות

| | כתובת | פורט פנימי |
|---|---|---|
| בוטי (מושיקו) | `https://bot.204-168-132-44.sslip.io` | 3000 |
| בוטי (אשתו) | `https://wife.204-168-132-44.sslip.io` | 3100 |

`sslip.io` הוא DNS ציבורי שממפה `<כל-דבר>.204-168-132-44.sslip.io` ל-IP שמקודד
בשם. בלי חשבון, בלי טוקן, ובלי מה שנשבר קודם — הכתובות לא מתחלפות לעולם.

Caddy (`/etc/caddy/Caddyfile`) עושה reverse proxy ומנפיק ומחדש אישורי
Let's Encrypt לבד. **שים לב:** חבילת Debian מפעילה את Caddy כבר בהתקנה, ולכן
`systemctl enable --now caddy` לא טוען קונפיג חדש. אחרי כל שינוי:
`systemctl reload caddy`.

המנהרות הזמניות (`trycloudflare`) כבר לא נחוצות לגשר. `cf-tunnel` הישן עדיין
רץ לשימושים אחרים.

## זיכרון — הסיכון האמיתי

3.8GB לשני מופעים, כשכל אחד גורר Chromium. `dmesg` מתעד שתי קריסות OOM
(9 ביוני, 29 ביוני) שבהן הרנדרר תפח ל-1.9GB ואז ל-3.3GB ונהרג.

מה נעשה:

1. **הוסר `--memory-pressure-off`** מדגלי Chromium. הדגל הזה אמר ל-Chrome
   להתעלם מלחץ זיכרון, כלומר לא לשחרר כלום ולתפוח עד שההרוג. זה היה הגורם.
2. **תקרה על ערימת ה-JS** — `--js-flags=--max-old-space-size=512`, ומגבלת
   שני תהליכי רנדרר.
3. **`/usr/local/bin/bot-memory-guard.sh`** רץ ב-cron כל שתי דקות (המקור:
   `ops/memory-guard.sh`). מודד **PSS ולא RSS** — סכימת RSS על תהליכי
   Chromium סופרת זיכרון משותף פעם לכל תהליך והראתה 3,033MB בזמן שהמכונה
   כולה השתמשה ב-2,204MB; סף שנקבע לפי מספר כזה מאתחל בוט בריא בלולאה.
   מאתחל מופע אחד בלבד, ומחכה דקה לפני שהשני בכלל נשקל.
   - רצפה מערכתית: פחות מ-400MB פנויים ← מאתחל את הגדול מבין השניים
   - תקרה למופע: מעל 1,400MB ← מאתחל אותו
   - יומן: `/var/log/bot-memory-guard.log`
4. **swap הוגדל** מ-2GB ל-4GB (`/swapfile2`, רשום ב-fstab).

מדידה טיפוסית אחרי השינויים: מושיקו ~1,270MB, אשתו ~400MB, פנוי ~1,450MB.

### בדיקה ידנית
```bash
/usr/local/bin/bot-memory-guard.sh && tail -5 /var/log/bot-memory-guard.log
```

### אם בכל זאת צפוף
`family-bot` רץ מאז מאי, תופס ~81MB, ואין לו אף תהליך Chromium. לא נגעתי בו,
אבל הוא המועמד הראשון לכיבוי אם צריך מקום.
